1. EXECUTIVE SUMMARY
================================================================================
GridSense is an autonomous, end-to-end distribution-feeder intelligence and 
monitoring platform engineered to solve critical operational challenges in modern 
electrical distribution networks. As distributed energy resources (DERs) like 
rooftop solar photovoltaics penetrate secondary distribution grids, traditional 
static hosting capacity limits become obsolete, causing unmonitored voltage 
swells, reverse power flow, and local transformer overloads.

GridSense bridges edge embedded sensing with cloud/edge AI intelligence:
1. An ESP32 microcontroller edge node reads feeder RMS Voltage, RMS Current, and 
   Renewables, computing a real-time Hosting Capacity Index (HI).
2. Telemetry is streamed over MQTT (1883) to a local Eclipse Mosquitto broker.
3. A robust Python bridge parses wire payloads and commits time-series data to 
   MySQL 8.0 with sub-second timestamps.
4. An AI Risk Engine evaluates real-time grid risk using an OpenRouter LLM 
   (openai/gpt-4o-mini) providing natural-language engineering diagnoses and 
   actionable mitigation recommendations, backed by a local Random Forest 
   classifier with 99.67% test accuracy for offline fault tolerance.
5. A FastAPI backend broadcasts merged telemetry and risk state every 2 seconds 
   over WebSockets (/ws/live).
6. A minimalist, dark-themed React dashboard presents real-time numerical 
   gauges, dynamic rolling trends, and instant event alarms.

All software components have been deployed, configured natively on Windows (no 
Docker), and verified end-to-end using simulated telemetry. The physical hardware 
firmware is fully written, validated, and ready for drop-in replacement on laptop 
integration day with zero code modifications downstream.

2. PROBLEM STATEMENT & BACKGROUND
================================================================================
Modern electrical distribution networks (230V single-phase / 400V three-phase 
secondary distribution) were historically planned for unidirectional power flow: 
substation -> feeder -> customer load. 

The rapid adoption of distributed solar photovoltaics has fundamentally inverted 
this paradigm:
- Voltage Volatility: High solar export during low daytime demand drives local 
  feeder voltages above statutory limits (>244V / +6%), threatening household 
  appliances and degrading insulation.
- Thermal Overload: Evening peak load curves without solar support cause high 
  current draws (>50A on local feeder branches), triggering thermal stress and 
  breaker trips.
- Lack of Dynamic Visibility: Distribution utilities typically rely on static 
  interconnection studies. They lack real-time Hosting Capacity Index (HI) 
  monitoring to dynamically regulate solar inverter inverters or dispatch 
  demand response.

GridSense provides this missing real-time visibility through low-cost IoT edge 
sensing, localized data persistence, and automated AI diagnosis.

3.1 Layer 1: Hardware Node & Sensor Simulation
- Script: `ingestion/fake_esp32.py`
- Firmware: `firmware/main.cpp`
- Wire Protocol: Comma-Separated Values: `voltage,current,renewable,hosting_index`
- Example Payload: `"230.12,30.45,55.00,89.20"`
- Publish Frequency: Exactly 2.0 seconds (500 mHz).
- The payload schema is byte-for-byte identical between the Python simulator and 
  the C++ ESP32 firmware, ensuring a seamless hardware swap.

3.2 Layer 2: Message Ingestion (MQTT Broker)
- Technology: Eclipse Mosquitto 2.1.2 (native Windows binary in `tools/mosquitto/`).
- Port: 1883 (TCP).
- Config: `mosquitto.conf` with `listener 1883` and `allow_anonymous true`.
- Ingestion Bridge (`ingestion/mqtt_to_mysql.py`):
  - Listens to topic `gridsense/feeder1/telemetry`.
  - Parses CSV strings into floating-point numbers.
  - Features error-handling traps: malformed payloads (wrong field counts, non-numeric 
    corruptions) are logged as warnings and skipped without crashing the bridge.

3.3 Layer 3: Time-Series Data Persistence (MySQL 8.0)
- Service: Native Windows service `MySQL80`.
- Database: `gridsense`
- Table Schema:
  CREATE TABLE feeder_telemetry (
      id BIGINT AUTO_INCREMENT PRIMARY KEY,
      timestamp DATETIME(3) DEFAULT CURRENT_TIMESTAMP(3),
      voltage DOUBLE NOT NULL,
      current DOUBLE NOT NULL,
      renewable DOUBLE NOT NULL,
      hosting_index DOUBLE NOT NULL,
      INDEX idx_timestamp (timestamp)
  );

3.4 Layer 4: AI & Machine Learning Risk Engine
- Service: `services/risk_api/main.py` (FastAPI running on port 8001).
- Dual-Inference Architecture:
  1. Primary Engine: OpenRouter LLM API (`openai/gpt-4o-mini`).
     - Prompt: System instructions as an electrical grid protection expert.
     - Output: Strict JSON with `risk_level`, `confidence`, `analysis`, and 
       `recommendation`.
  2. Fallback Engine: Local Scikit-Learn `RandomForestClassifier` (`ml/risk_model.pkl`).
     - Trained on 6,000 synthetic feeder operating regimes.
     - Held-out test accuracy: 99.67%.
     - Microsecond latency fallback in case of Internet connectivity loss.

3.5 Layer 5: Backend Orchestration & Streaming API
- Service: `services/backend_api/main.py` (FastAPI running on port 8000).
- Endpoints:
  - `GET /latest`: Returns the most recent telemetry point + risk prediction.
  - `GET /history?minutes=15`: Returns rolling historical time-series array.
  - `GET /risk`: Direct risk evaluation snapshot.
  - `POST /simulate-surge`: Allows injecting test voltage/load spikes from the UI.
  - `WS /ws/live`: Async WebSocket streaming live packets to connected dashboards 
    every 2 seconds. Features in-memory risk caching to ensure the WebSocket loop 
    is never blocked by network latency.

3.6 Layer 6: Minimalist Dashboard Interface
- Directory: `frontend/` (Vite + React 19 + Tailwind CSS + Recharts).
- Design Concept: Minimalist, clean, high-contrast dark palette (`#090d16`).
- Key Features:
  - 4 Monospaced KPI Cards: Voltage (V), Current (A), Renewables (%), Hosting Index.
  - AI Risk Status Banner: Dynamic color pill (Safe / Caution / Critical),

  - Dual-Axis Rolling Line Chart: Synchronized Voltage (Cyan) and Current (Amber)

  - Live Event Log: Automatically captures caution and critical occurrences.
  - Controls: Stream Pause/Resume toggle and interactive "Test Surge" simulation button.

4. MATHEMATICAL MODELS & GRID PHYSICS FORMULATIONS
================================================================================

4.1 Standardized Hosting Capacity Index (HI) Equation
The Hosting Capacity Index is a continuous metric normalized between 0.0 and 100.0, 
quantifying the available feeder margin before operating limits are violated:

  HI = max(0, min(100, 100 - (P_voltage + P_current + P_renewable)))

Where:
1. Voltage Deviation Penalty (P_voltage):
   P_voltage = (|V - 230.0| / 20.0) * 40.0
   - At nominal 230V: P_voltage = 0.
   - At statutory limit boundary (210V or 250V): P_voltage = 40.0 pts.

2. Thermal Current Loading Penalty (P_current):
   P_current = max(0.0, (I - 35.0) / 25.0) * 35.0
   - Below continuous nominal rating (35A): P_current = 0.
   - At rated feeder breaker limit (60A): P_current = 35.0 pts.

3. Renewable Stress & Reverse Power Flow Penalty (P_renewable):
   If Renewable > 60% AND Voltage > 235V (Solar Swell Condition):
     P_renewable = ((Renewable - 60.0) / 20.0) * ((V - 235.0) / 10.0) * 25.0
   Else if Current > 45A AND Renewable < 30% (High Load / Low Generation):
     P_renewable = ((30.0 - Renewable) / 20.0) * 15.0
   Else:
     P_renewable = 0.0

4.2 Feeder Risk Classification Matrix
Grid states are categorized into three standardized operational tiers:

+--------------+------------------+------------------+-------------------+
| Risk Level   | Voltage (V)      | Current (A)      | Hosting Index     |
+--------------+------------------+------------------+-------------------+
| SAFE         | 220.0V - 240.0V  | <= 40.0A         | HI >= 70.0        |
| CAUTION      | 214V-220V or     | 40.0A - 52.0A    | 40.0 <= HI < 70.0 |
|              | 240V-244V        |                  |                   |
| CRITICAL     | < 214V or > 244V | > 52.0A          | HI < 40.0         |
+--------------+------------------+------------------+-------------------+

5.3 SCT-013-000 Burden Resistor & DC Bias Circuit
The SCT-013-000 produces an AC current output (50 mA at 100 A primary). Because 
the ESP32 ADC cannot read negative voltages (-3.3V to 0V):
1. The 33 Ω burden resistor converts the 50 mA current into an AC voltage:
   V_peak = I_secondary_peak * R_burden = (0.050 A * 1.414) * 33 Ω = 2.33 V peak-to-peak.
2. A voltage divider using two 10 kΩ resistors from 3.3V to GND establishes a 
   1.65 V DC virtual ground.
3. A 10 µF capacitor is connected from the 1.65V divider node to GND to filter AC noise.
4. One lead of the SCT-013 connects to the 1.65V node; the other lead connects 
   to GPIO 35. The resulting waveform oscillates between 0.48V and 2.82V, safely 
   within the ESP32 ADC range (0V to 3.3V).

5.4 Potentiometer Bench Simulation Setup

- Potentiometer 2: Wiper to GPIO 35 (simulates 0A - 60A load current).
- Turning the potentiometers triggers real-time color transitions on the physical 
  LEDs, OLED readouts, and dashboard alarms.

7. OPERATIONAL GUIDE
================================================================================

7.1 One-Click Launch (PowerShell)
From the project root:
```powershell
powershell -ExecutionPolicy Bypass -File gridsense\scripts\run_all.ps1
```
This starts Mosquitto, Ingestion Bridge, Simulated ESP32, Risk API, Backend API, 
and launches the React frontend at `http://localhost:5173`.

7.2 Manual Startup Instructions
To run individual services in dedicated terminals:
1. Mosquitto Broker:
   & "$env:USERPROFILE\tools\mosquitto\mosquitto.exe" -c gridsense\mosquitto.conf -v
2. Ingestion Bridge:
   python gridsense\ingestion\mqtt_to_mysql.py
3. Simulated ESP32 Publisher:
   python gridsense\ingestion\fake_esp32.py
4. AI Risk Microservice:
   python -m uvicorn services.risk_api.main:app --host 127.0.0.1 --port 8001
5. Backend Orchestration API:
   python -m uvicorn services.backend_api.main:app --host 127.0.0.1 --port 8000
6. React Frontend:
   cd gridsense\frontend && npm run dev

7.3 Model Retraining Workflow
To retrain the local Random Forest model against real historical data stored in MySQL:
1. Query MySQL records:
   SELECT voltage, current, renewable, hosting_index FROM gridsense.feeder_telemetry;
2. Save rows to `gridsense/ml/feeder_training_data.csv`.
3. Run training:
   python gridsense/ml/train_model.py
4. The updated model is saved to `gridsense/ml/risk_model.pkl` and reloaded 
   automatically by `risk_api`.

8. LAPTOP INTEGRATION CHECKLIST (HARDWARE HAND-OFF)
================================================================================
When transitioning from simulation to real hardware:

[ ] Step 1: Connect laptop and ESP32 to the same WiFi network.
[ ] Step 2: Run `ipconfig` (Windows) or `ifconfig` (Mac/Linux) to find laptop IP 
            (e.g., `192.168.1.105`).
[ ] Step 3: Open `gridsense/firmware/main.cpp` and update line 40:
            const char* WIFI_SSID     = "Your_WiFi_SSID";
            const char* WIFI_PASSWORD = "Your_WiFi_Password";
            const char* MQTT_BROKER   = "192.168.1.105";
[ ] Step 4: Flash `main.cpp` to ESP32 DevKit V1 using Arduino IDE or PlatformIO 
            (Baud: 115200).
[ ] Step 5: Wire sensors according to Section 5.2 pinout table.
[ ] Step 6: Stop `fake_esp32.py` on the laptop.
[ ] Step 7: Power on ESP32.
[ ] Step 8: Verify real sensor readings stream to Mosquitto, insert into MySQL, 
            and update the React dashboard with ZERO changes to the downstream code!
